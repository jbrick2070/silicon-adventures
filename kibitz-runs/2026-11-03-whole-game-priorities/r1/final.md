# Whole-game design priorities
## 1. Spend the next sprint on trustworthy puzzle feedback
Give Saber room to discover the original puzzles. When a player explicitly asks for help, the advice should describe a decision they can actually make in the room they occupy. Water is the first test. The same player who successfully navigated to the submarine controls can currently be directed to the Hurk office before the ship has left. A second documented run lost a chip 106 recorded inputs separate from its later use in the successful run. These establish impact and a reproducible defect, not a population-wide loss rate. See evidence.md in the campaign folder.

## 2. First playable slice
Extend the existing Where next? button with local contextual hints only in computer 9709 and control 23272. Reading a clue costs zero engine turns. The player still operates every switch. Reuse the journal, with three levels of voluntary disclosure. One press describes what to examine, the next interprets the present evidence, the third supplies a local action only when warranted.
- Computer: inspect state.objects and state.inventory by numeric ID. Installed part 2718 takes priority. A loose chip 13010 in the pack allows an insertion clue. A loose chip present on this floor is a visible lead. With neither, say what is missing and invite a check of earlier journal entries. The beach is an original search location, never a verified current location. Show no invisible thief and promise no restore point. At the machine, clicking the installed part can remove it.
- Controls: consult the local room before the global milestone; visiting sub deck 28593 is insufficient for piloting success. In scope, keep the clue grounded in this room even after ScepterHints.current has selected Hurk. Label the existing left/centre/right sprites by their archive IDs 4876/13165/20759. Relate what the player sees in the viewplate to the manoeuvre, preserve text-only play. At the exact level, name an individual action only for an unambiguous, tested stage. Never print an unconditional five-click recipe on a returned or partially piloted boat. Hatch and repair conditions are off-screen from control. If the local snapshot cannot establish the next safe move, withhold it.
- Implementation sketch: pure room helper in game/hints.js using scene, objects and inventory. Return a stable contextual key and display-only tier strings. game/play.js whereNext() chooses that result before the existing 19-milestone fallback. Reset the reveal rung when context changes. Render local prose separately from legacy exact-input arrays and their “Exactly” prefix. No API calls from the helper, no new session state persisted, no unseen map markers.
- Verification: old hints still pass check_hints.py. Add a narrow browser-JS or Node fixture for the two rooms including working machine with empty pack, chip held/on floor/unknown, visit-to-deck before control and ambiguous control returns. Verify typed clues/click IDs against the correct room and disk script, including detours and failures. Check the existing closed-hatch prepared voyage, a bookmark, and a restore in an isolated muted test session when implementing. An incorrect clue at any reachable stage blocks release.

## 3. Order for the next design passes
1. Water puzzle feedback as above. Success means the player can identify their *next local decision* without stale chapter advice, automatic actions or a spoiler on entry.
2. Protect decisions in dialogue and explain what Restore will return to. Start with the Guard/King yes/no Travel leak and the misleading “last manual save” wording. Keep intentional typed answers and deliberate refusals. Evaluate free-form riddles separately before disabling any verbs. Test keyboard, pointer and touch against the same original consequences and compare manual save followed by doorway checkpoint. The player should be able to distinguish turning in the picture from sending a turn.
3. Let returning players find their own way. Observe the first south exit from quarters and a later return to Elron. If players cannot recognize rooms already visited on touch, prototype a tap-to-read visited room name on the existing chart. Preserve fog and scripted exits. Compare with a single line explaining how to reach Travel before changing the cover hierarchy.
4. Give one troublesome scene an art pass only after observing an error. Test recognition of the dock pilings or weapons rack post at native size while walking. Use a single reversible foreground trial with Original registration, intact sprite anchors, two-colour output and the existing layer checks. Continue with further rooms only on demonstrated benefit.
5. Observe combat/rest and the homecoming. Earth has the riddle, Air the click traps, Fire a costly battle, and the return two gate challenges. Existing weapons, repeat attack, map, four-scepter count, return gates and Finale already supply most proposed mechanisms. Put a short blind trial at one decision in each arc before funding any new overlay or ending content.

## 4. Deciding what ships
Compare an unaided first-time player and a returning player if available. Record the room, visible evidence, action attempted, unintended engine turns, hint tier requested and whether the original puzzle still makes sense. In the absence of players report only deterministic fixture outcomes. Promote dialogue or save clarity above the next Water expansion if repeated errors occur outside Water. Keep the 78 documented class boxes, full campaign replay and other prospective work distinct from new implementation. During future tests confirm a save under a temporary Java home before relying on the server, click Sound off before a game and never play cues. Preserve original art, saves, Java and the Windows zip.
